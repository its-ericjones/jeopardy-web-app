# Technical Overview

## Architecture Summary

The app is a static browser application with three core files:

- `jeopardy.html`: page structure, controls, modals, game board, score table.
- `css/jeopardy.css`: layout, forms, buttons, board styling, modal styling, responsive rules.
- `js/jeopardy.js`: parsing, validation, file import/export, board generation, gameplay, scoring, local storage, answer key printing.

There is no build process, package manager, server, database, or external runtime dependency.

## Runtime Model

The browser loads:

1. `jeopardy.html`
2. `css/jeopardy.css`
3. `js/jeopardy.js`

The JavaScript then attaches event listeners, initializes or restores saved state, and dynamically builds the form and board content.

## Main UI Areas

### Start Controls

The starting screen has three options:

- `Create`: show the manual game creation form.
- `Edit`: open a draft or game file into the form.
- `Play`: open a complete game file and proceed to team setup.

### Create Form

The create form includes:

- Game title
- 5 generated category sections
- 5 generated clue rows per category
- Team setup
- Validation message area
- `Create` and export action area

The form structure is generated dynamically by `addCategory()`.

### Game Board

The playable board is a 5 by 5 table. The table structure exists in HTML, and the cells are generated by JavaScript.

Each generated board cell contains:

- Visible point value
- Hidden clue text
- Hidden response text

Clicking a cell opens the prompt modal.

### Prompt Modal

The prompt modal shows:

- Clue
- Hidden response
- `Show Answer`
- Team selector
- Add/subtract scoring buttons
- Cancel button

Scoring marks the cell as used and saves the board state.

### Score Table

The score table is shown only when a board is loaded. It supports:

- Team name edits
- Score display
- Manual add/subtract controls
- Prompt-based add/subtract scoring

## Data Flow

### Create Flow

1. User clicks `Create`.
2. App initializes the form.
3. User fills in title, categories, clues, responses, and teams.
4. App updates the action state as fields change.
5. User clicks `Create`.
6. App validates the complete form.
7. App builds game text.
8. App stores the board text and title in local storage.
9. App generates the playable board.

### Edit Flow

1. User clicks `Edit`.
2. Browser file picker opens.
3. App reads the selected `.txt` file with `FileReader`.
4. App validates it as an editable draft.
5. App parses title, teams, categories, clues, and responses.
6. App fills the create form.

### Play Flow

1. User clicks `Play`.
2. Browser file picker opens.
3. App validates that the selected file is a complete game file.
4. App stores the board text and title.
5. App shows team setup.
6. User clicks `Continue to Game`.
7. App generates the board.

### Export Flow

See [Export Workflow](export-workflow.md) for the dedicated export documentation.

## Local Storage

The app uses browser `localStorage` for persistence.

Known storage keys include:

- `jeopardyBoard`: saved complete board text.
- `jeopardyTitle`: saved board title.
- `jeopardyTeams`: team names and scores.
- `jeopardyUsedCells`: board cells that have already been played.
- `jeopardyFormDraft`: saved form draft data.

Local storage is browser-specific and device-specific. It is not shared across browsers or computers.

## Parsing

The parser reads plain text and returns structured board data:

```text
Title: ...
Category: ...
POINTS|CLUE|RESPONSE
```

The parser ignores blank lines and draft metadata lines. It accepts the first two pipe-separated fields as point value and clue, then joins remaining fields into the response.

## Validation

The app has two different validation levels:

- Draft validation: permissive, because drafts can be incomplete.
- Game validation: strict, because play requires a full 5 by 5 board.

Form validation also controls button state:

- Incomplete form: `Export Draft`, no `Create`.
- Complete form: `Create` and `Export Game`.

## Answer Key Generation

Answer key generation has three stages:

1. Parse the board text.
2. Build answer key HTML.
3. Inject print-only styles and call `window.print()`.

The app temporarily changes `document.title` to improve Safari's suggested PDF filename.

## Error Handling

The app uses a custom modal helper named `CustomDialog` for:

- Alerts
- Confirmations
- Success messages
- Error messages
- The intermediate answer key prompt

This avoids relying on browser-native alert styling and keeps the experience consistent.

## Browser APIs Used

- `FileReader` for reading local `.txt` files.
- `localStorage` for saved state.
- Programmatic anchor downloads for `.txt` exports.
- `window.print()` for answer key PDF/print output.
- DOM APIs for dynamic form, board, modal, and style creation.
